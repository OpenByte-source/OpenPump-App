# The Epic Hydro PE Pump (ZD21) protocol

For the full picture, see [the pump control guide](../pump-control-guide.md).

What OpenPump sends to and receives from a ZD21_PUMP over Bluetooth LE, as implemented in
`core/src/main/java/org/openpump/Proto.java` and modelled by `SimPump.java`. Everything
here is observable on the wire; nothing is copied from any manufacturer software.

Status: **verified** against a real device (a live capture of several hundred frames).

## Discovery and connection

| Item | Value |
|---|---|
| Advertised name | `ZD21_PUMP`, or `ZD21_PUMP_OTA`. OpenPump accepts both and treats them the same. What makes a pump advertise the second name, and whether the pump behaves any differently under it, is unknown; OpenPump sends nothing to do with firmware updates. |
| Service | `0000fff0-0000-1000-8000-00805f9b34fb` |
| Write characteristic | `0000fff1-0000-1000-8000-00805f9b34fb` |
| Notify characteristic | `0000fff4-0000-1000-8000-00805f9b34fb` |
| Enable telemetry | write the CCCD `00002902-…` of `fff4`: notifications (`01 00`), or indications (`02 00`) if that is all it offers |

## Commands (phone → pump)

Every frame starts `66 2A <opcode>`.

| Opcode | Name | Payload | What comes back | Notes |
|---|---|---|---|---|
| `0x2B` | Add preset | speed, upper kPa, upper hold s, lower kPa, lower hold s (one byte each) | `2B 01` | **Appends** to the preset table. An all-zero preset is **not stored** — see below |
| `0x2A` | Delete preset | index | `2A 01` | **Compacts** the table (later entries shift down). Deleting the entry that is running does not stop it — see below |
| `0x2C` | Start preset | slot 0–8 | `2C 01`, or **`2C FD`: refused** | The pump then cycles that preset on its own. An empty slot is refused |
| `0x2D` | Stop | — | **unknown** — see below | **Vents** — a release, not a pause |
| `0x29` | List presets | — | the table itself, not `29 01` — see below | |
| `0x25` | Set time | not established | not established | OpenPump never sends it |

What comes back, and what it means:

- **Add, Delete and Start** are acknowledged with `<opcode> 01`. A reply names no Start, so
  OpenPump gives each Start reply every Start it may be for - replies keep the Starts' order,
  and come within 5 s of the write (the log's slowest is 1033 ms) - and takes it as one Start's
  only when it can be no other's. The other acks are only logged.
- **The pump refuses.** A Start of an empty slot is answered **`2C FD`** (`Proto.REFUSED`),
  and the pump carries on with whatever it was running. The owner's log of 22 September 2026
  has 23 of them. Only `2C FD` has been seen, but OpenPump reads `<opcode> FD` as a refusal
  for every command. A live change goes in force only on its Start's `2C 01`; refused, it is
  undone on screen and the person is told. An FD for any other Start, or one that may be for
  several, is a refusal too: OpenPump writes the table again and sends what was confirmed, and
  stops the run if the pump refuses that as well. A refused Start leaves the pump on what it ran
  before - after a step's Start, the step before - and OpenPump counts that in what the pump may
  be running.
- **Replies go missing, and the command still happens.** The same log has 343 Starts and 319
  replies; the guided start's Starts pulled the cuff to about 17 kPa with none, and replies were
  lost in bursts. No reply is not a refusal: OpenPump sends what was confirmed again, so the pump
  and the screen agree whichever way the lost Start went, and holds a new live change back while
  any Start may still be answered.
- **Stop:** whether the pump acknowledges *every* stop — under pressure, during its own
  release, when idle or already vented — is **unknown** (release checklist H15, not yet
  run). OpenPump never waits for a stop's ack: only the pump's readings confirm a vent.
- **List** is answered by the table dump: `29`, then five bytes for each stored preset in
  slot order, in the same field order as an Add, with no count byte (an empty table is the
  single byte `29`). This is the layout OpenPump parses (`Validate.parseDump`); only the
  hardware validation routine and the self-test send List.
- A reply can still go missing, so silence proves nothing either way. For anything but a
  Start, an ack says a frame arrived, not what the pump did with it.
- **An all-zero preset is not stored.** `66 2A 2B 00 00 00 00 00` leaves the table as it
  was, so every later Add sits one index lower than a count of the Adds says. This is
  inferred from the owner's log of 22 September 2026: all 280 answered Starts in it match a
  table without the zero entries, and 23 of them (the refusals) cannot be explained with
  them. Whether the zero Add itself is acknowledged can't be told from that log. OpenPump
  never writes one: a batch ends at a rest.

- **Preset table:** 9 slots.
- **Pressures** in commands are **whole kPa**, 0–57. Holds are seconds, 0–255 — one
  byte, so a hold longer than 255 s is built from several presets (see `Model.Set`).
- **Speed** is a 0–255 code, never a raw percentage: `code = (pct × 255 + 50) / 100`;
  decode `pct = (code × 100 + 127) / 255`.

## Telemetry (pump → phone)

About 4 samples per second once notifications are on, as ASCII:

```
#<mode>,<deci-kPa>,<speed code>,<intelligent flag>
#AUTO,-189,179,0        → 18.9 kPa of vacuum, speed 70 %
```

- Pressure is **deci-kPa** and **negative on the wire** (it is a vacuum); OpenPump uses
  the magnitude.
- A reading of **0.0 means "no measurement"**, not ambient pressure. It must never be
  integrated into a dose or used for a slope.

## Behaviour worth knowing

- **Stop vents.** It is a release, not a pause, and the pump's readings show the fall
  (release checklist H10: pass, from the owner's log). The rate was measured once, at
  about **4.68 kPa/s**, in one hardware log (2026-08-16), and has not been re-measured
  since; the hardware validation routine (step 3) measures it. OpenPump uses 4.68 as the
  fall it expects (`SessionActivity.VENT_RATE`).
- The pump **coasts** during a long upper hold (it pulls once and holds the valve; the
  pressure drifts down slowly rather than being topped up). **How fast is unknown**: one
  early hardware log shows a drift from 13.1 to 9.0 kPa, and no measurement of the rate
  has been made (release checklist H14). The simulator's 0.014 kPa/s is its own choice,
  not a measurement.
- Whether the pump plays two **adjacent presets without a break** — no release, re-pull or
  pause where one hands over to the next — is **unknown** (the seam test, release checklist
  H16, not yet run). A hold longer than 255 s is sent as several presets back to back, so
  it depends on this.
- **Deleting the running entry does not stop it.** The pump keeps cycling the preset it
  was started on after that entry is deleted, until the next Start or a stop (release
  checklist H13, observed in the owner's log of 22 September 2026: a warm-up step's entry
  was deleted and the step kept cycling for 54 s, to the next Start). OpenPump's simulator
  does the same.
- Once a preset is started the pump keeps cycling it **by itself**; the phone is what
  moves it on to the next preset and what stops it. This is why OpenPump treats a lost
  Bluetooth link as dangerous (see SAFETY.md).
